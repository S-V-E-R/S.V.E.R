## Boundaries and legacy carryover

One Rust/Axum service, SQLx/Postgres and a Next.js client in this repository. This specification covers Login. `C:\streaming\SVER` is the behavior reference. Its `auth.service.ts`, `auth.password-reset.ts`, `oauth.service.ts`, `oauth.link-transaction.ts`, `2fa.utils.ts`, identity/security schemas and lifecycle tests were inspected. CodeGraph requests encountered its concurrency limit; direct source inspection was used for those reads.

Port: normalized unique emails and usernames, ownership-checked provider linking, last-method protection, single-use challenges, reset session revocation, authenticator/recovery behavior and transactional account locks. Replace: JWT/refresh-token infrastructure with the approved opaque Postgres session cookie, Prisma with SQLx, and the old UI with Next.js. Leave out: legacy registration hooks for currencies, progression, advertiser/agency accounts, stream records and CrowdSync.

The database is separate from legacy and local development. IDs are text to accommodate legacy IDs; password hashes are nullable. Argon2 and bcrypt verification are supported. Bcrypt is upgraded only after successful full authentication. Signup policy never applies to existing-password verification. The `sver-import-check` command defaults to rehearsal in a disposable local schema. Its explicit live modes check/roll back or commit against the guarded sver.tv target; the authorized live import is complete. Legacy TOTP uses AES-256-GCM with a 16-byte nonce and `iv:tag:ciphertext`; import decrypts it with the preserved key and reencrypts the same seed with the live key. Original account/profile fields and all linked-identity metadata are retained in `legacy_account_data` for later modules. Provider access/refresh tokens are excluded from active import; the original full backups are preserved.

Legacy soft-deleted accounts retain their original deletion timestamp and receive `legacy_deletion_hold`: they cannot authenticate, recover, restore themselves or enter automatic erasure. Any later change to that hold requires explicit migration review. An enabled authenticator with no stored secret uses the user's permitted migration fallback, recorded per account in the private report and metadata; working authenticators remain enabled. These changes were exercised only in disposable rehearsal data, not on legacy accounts.

## Exact rules

- Sign-in: email **or username** plus password in one case-insensitive, whitespace-trimmed field, or Google/Twitch/Discord OAuth. The password endpoint accepts `identifier` (and the previous `email` field as an API compatibility alias). Both identifiers share a user-ID-based failed-login counter; switching identifiers or IPs does not reset the account cooldown. Signup and password recovery still collect an email address.
- Signup: email, username, date of birth and password, or a supported provider. At the user's October 3 request to restore the legacy flow in the new design, provider buttons now start OAuth directly from either login or signup without validating the email-registration form. Existing identities proceed to their usual sign-in/MFA path. A new provider identity returns to `/oauth-signup` with a suggested username; the user confirms username/date of birth and Turnstile before an account or authenticated session is created. No email/password entry is required for provider signup. Email signup retains its age check before persistence.
- The provider-first flow supersedes the earlier requirement to collect age before OAuth state: only encrypted, short-lived provider proof is held until completion, with a hashed token in `oauth_signups` and a Secure/HttpOnly/host-only cookie in production. It expires after ten minutes, is consumed transactionally and is cleaned by the existing worker. Underage completion cannot create an account. Existing email addresses never auto-link, and provider email-verification requirements remain enforced.
- Username: 3–25 ASCII letters, digits or underscores, case-insensitive uniqueness, reserved site/faction/staff names and a maintained abuse list. Availability updates after 350 ms without typing, using the same server naming policy and live account lookup. Taken and held/deleted account names remain unavailable. The public `GET /api/auth/username-availability?username=...` endpoint returns availability/message only, is not cached and permits 60 checks per client IP per minute. Availability does not reserve a name; the database uniqueness constraint remains authoritative at account creation. Existing migrated names remain unchanged.
- Password: 10–128 characters, at most 512 UTF-8 bytes; no arbitrary composition rules. New/reset passwords use Argon2id and a padded HIBP range lookup (only the first five SHA-1 hex characters leave the server). A failed breach check fails closed. Legacy password checks do not enforce signup length or breach policy.
- Turnstile: server validation for signup and recovery requests, hostname/action checking, five-minute single-use tokens. Development uses Cloudflare's official test keys; production rejects them.
- Email: verification 24 hours, reset one hour, hashed single-use tokens, encrypted Postgres mail jobs delivered by Resend with idempotency keys and bounded retries. Resends have a 60-second cooldown. Without a Resend key, local development holds mail in the local database for preview; with a configured key and sender, it sends through Resend. Tokens are not printed to logs. Links use URL fragments to avoid token leakage into request URLs/referrers.
- Reset: sets a password even on an OAuth-only account after mailbox proof; revokes **all** sessions and outstanding authentication challenges, matching the legacy security behavior. MFA remains enabled and is required at the next login. Reset never signs the user in.
- Sessions: random 256-bit opaque token, SHA-256 stored, HttpOnly SameSite=Lax host-only cookie; Secure in production, 30-day rolling expiry. JSON mutations require the exact configured Origin. Account operations lock the user row and recheck the session/version. Password hashing runs outside the async executor with bounded concurrency.
- Rate limits: five credential attempts per account and per socket IP in a fixed 15-minute window, successful attempts released from the counters. Attempts are reserved before expensive work to prevent concurrent bypass. A full window returns 429 with Retry-After until the window ends; blocked retries do not extend it. This intentionally applies the accepted same-IP rule even behind shared networks. Additional endpoint/IP limits protect signup, recovery, OAuth and MFA. Forwarded IP headers are ignored unless an explicitly configured trusted proxy is the socket peer.
- TOTP: six digits, SHA-1, 30-second steps, ±1 step drift, replay rejected. New enrollment generates 160-bit seeds; verification also supports the existing 80-bit otplib seeds without changing them. Ten new recovery codes, displayed once, hashed and consumed atomically; imported bcrypt recovery hashes and their remaining counts are preserved. Setup expires after ten minutes and requires recent primary authentication; existing MFA must be proved before sensitive changes. Losing both authenticator and recovery codes requires an audited support/migration recovery process; password reset alone does not disable MFA.
- Sensitive changes: primary authentication within five minutes plus a fresh MFA code when enabled. Password users reauthenticate with a password; OAuth-only users reauthenticate with an already-linked provider. Enabling/disabling/regenerating MFA revokes other sessions and outstanding login challenges. Disabling MFA immediately removes streaming eligibility. No stream keys are issued by this module; future media routes must use its verified-email/MFA authorization guard.
- Deletion: recent primary proof and fresh MFA, then 14-day grace and revoke all sessions/challenges. Credential login during grace grants only the cancellation screen. Cancellation restores access and creates a fresh session. After the deadline login/cancellation fail; the scheduled worker deletes the account and cascades Login data. Other modules must extend erasure when they add owned data. Legacy soft-deleted accounts need explicit import handling and must not accidentally enter the new erasure queue.
- OAuth: confidential backend authorization-code flow; one-use state, browser-bound cookie, ten-minute expiry, exact callback URI, no tokens sent to the frontend. Google/Discord use S256 PKCE; Twitch uses its documented client-secret/state flow. Provider configuration is required before a button is enabled. Provider tokens are used only to fetch identity and are not retained. Google/Discord signup requires the provider's verified-email flag. Twitch exposes no verification flag, so its accounts receive a SVER verification link and remain unverified until it is used. An existing email never auto-links: sign in to that SVER account, then link from settings. Existing identity sign-in does not replace the account email or profile. Every OAuth sign-in still enforces local MFA/deletion state. Link callbacks revalidate the originating session under the account lock. Provider reauthentication must return the already-linked subject. Unlinking revokes other sessions and outstanding challenges, preventing a pending login from completing through the removed provider.

## Account changes

Added October 9, 2026 (gaps from the legacy audit: legacy let people change their password and email while signed in; GDPR and CCPA need a copy of your data).

- **Password.** `POST /api/auth/password/change` sets a new password, or adds one to a provider-only account. It needs the usual security step-up (a sign-in confirmed in the last five minutes, plus a fresh authenticator or recovery code when 2FA is on) and the same rules as signup (10–128 characters, breached passwords refused). Every other device is signed out.
- **Email.** `POST /api/auth/email/change` sends a 24-hour link to the new address, with the same step-up. The address changes, already verified, only when that link is opened on `/verify`; the link works once, and the address is checked for another account again then. The reply is the same whether or not another account uses the address. `DELETE` cancels a pending change; `/api/auth/me` shows it masked (`c***@example.com`). At most 3 requests an hour.
- **Security notices.** A password change, an email change request and a completed email change each send a notice to the account's address at the time, naming the new address only masked. Notices survive the session reset a password change causes.
- **Your data.** `GET /api/auth/export` (sign-in confirmed in the last five minutes; 3 a day) downloads a JSON file with a short readme: the account row and every row of every table keyed to the account (`user_id`, `author_id`, `follower_id`, `owner_id` and similar columns, found from the schema, so new tables are included automatically). Sign-in history comes from `sessions` without token digests. Left out: credentials, anti-abuse signals (integrity cases, MAGNet flags), staff internals, tables holding other people's personal details (copyright claimants, guardian consents, Take It Down records), and any column that looks like a secret, key or network address. Up to 10,000 rows per table.

Done when: a password change signs out other devices and the new password works; an email change takes effect only from the link sent to the new address and only once; each change sends its notice; the export contains the account and its rows and no secrets. Covered by `tests/login.rs` (`exercise_account_changes`).
